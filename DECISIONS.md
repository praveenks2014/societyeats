# DECISIONS.md — assumptions & pragmatic choices

Every non-obvious call made while building GharSe in one session, and why.

## Stack & infrastructure

1. **PGlite dev fallback.** The spec mandates Postgres via `DATABASE_URL` (kept as the primary path, used on Replit). When the variable is unset, the app falls back to an embedded PGlite (WASM Postgres) at `./.data/pglite` with auto-migrate + auto-seed. Rationale: the build machine and fresh clones have no Postgres, and "fully clickable tonight" beats "install a database first". Same Drizzle API both ways; no native binaries either way.
2. **No middleware.ts.** Role checks live in layouts (`/seller`, `/admin`, `/restaurant`) and in every API handler via `requireSession(roles)`. Simpler than edge middleware and avoids edge-runtime DB access.
3. **Hand-rolled service worker** instead of `@ducanh2912/next-pwa`: fewer build-time moving parts, and the spec explicitly allowed it. It precaches an offline shell, uses network-first for navigations, SWR for images, and never caches `/api/*`.
4. **SVG PWA icons.** Chrome accepts SVG manifest icons; shipping raster PNGs would need an image toolchain. Swap in PNGs later if older Android install banners matter.
5. **`.replit` committed** so "Import from GitHub" runs with zero changes (dev run + autoscale deployment config).

## Product behaviour

6. **Single-vendor basket** (like Swiggy): a cart holds items from one kitchen/counter at a time; adding from another prompts "start a new basket?". Keeps delivery quotes, commission math, and seller queues coherent.
7. **Dispatch happens at "Mark ready"**, not at accept — closest to how food actually meets riders, and it makes the chaos-toggle demo a single button press.
8. **Mock tracking is clock-derived** (dispatch timestamp encoded in the mock provider order id): rider assigned <1 min, picked up 1–3 min, in transit afterwards, then "arrived — share OTP". No timers, no workers, survives serverless restarts.
9. **Delivery quotes are deterministic** in mock (distance-based, per-provider pricing personality, clamped ₹30–₹70) so the checkout preview and the charged amount always agree. The ~15% simulated failure applies to `createDelivery` only.
10. **Order cannot be delivered without the OTP**; in mock, the buyer's tracking screen hosts the simulated "rider handset" input. Mall pickups verify the OTP from the restaurant console instead.
11. **Rejecting a paid order → `refund_pending`** and the payment row flips to `refunded` immediately in mock; live mode would call Razorpay's refund API (stub noted in code).
12. **Ratings aggregate on seller profiles** (running average + count) and only home-kitchen orders affect them; mall counters keep FSSAI display but no rating field (out of scope).
13. **Buyer location is client-held** (localStorage) and sent as query params; the server re-validates the 10 km rule at quote time *and* order time from the address coordinates, so the radius cannot be spoofed by skipping the UI.
14. **FSSAI-pending grace window**: enforced lazily at browse time (no cron) — when a pending kitchen's newest application is older than `fssaiPendingMaxDays`, its listings are set inactive during the next browse query.
15. **Admin "grant" sets a 1-year expiry** from the grant date (typical minimum FSSAI validity) since the real certificate isn't parsed.

## Integrations

16. **Live API shapes are best-effort from public docs** (Porter UAT gateway, Shadowfax Flash, Borzo business API 1.6, Surepass FSSAI) and every live branch is marked `// VERIFY against partner docs when keys arrive`. None execute in MOCK_MODE.
17. **Razorpay capture is idempotent and race-safe**: the client-side signature verify handler and the webhook both funnel into `markOrderPaid`, which no-ops unless the order is still `placed`.
18. **Settlements (Razorpay Route)** are Phase 2: interface stubbed in `src/lib/payments/settlements.ts`, earnings page shows the "T+1 via Razorpay Route — coming soon" ledger note.
19. **Notifications are in-app only** (bell + 25s polling + toasts). Web push needs VAPID keys and a push service; the `notify()` helper is the single seam where push/MSG91 SMS would plug in.
20. **Uploads go to `/public/uploads`** with type/size validation; README flags the swap to object storage for production. Seeded FSSAI "documents" reference a committed placeholder SVG so the admin queue renders without uploads.

## Data & seed

21. **Society coordinates are approximate** (Nallagandla ↔ Narsingi ≈ 8.9 km apart) so cross-society browsing sits just inside the 10 km radius — deliberately, to demo distance chips both near and far. GVK One (Banjara Hills) is ~15 km from both, keeping mall counters out of home-delivery browse.
22. **Unsplash photo IDs are best-effort**; every image renders through a `FoodImage` component that falls back to a brand-styled placeholder on 404, so a dead URL never breaks the UI.
23. **Money is integer paise everywhere**; display formatting is `en-IN`.
24. **Demo login phone numbers** follow the spec's "demo accounts" intent: buyer 9999999901, seller 9999999902, restaurant 9999999903, admin 9999999904 (password `demo1234`), plus five more sellers and two more restaurant managers on 99999999xx.

## Schema extensions beyond the spec

25. Added `order_events` (timeline), `notifications`, `ratingCount` on seller profiles, `priority` + `chaosForceFail` on `provider_health`, and `titleSnapshot` on order items (order history survives listing edits). All additive.
26. `orders.status` gained `delivery_unassigned` (spec §7.3 requires the state; the enum in §5 didn't list it).

## Pilot Hardening v2 — Founder-Specified Fixed Decisions

The following were decided by the founder before this build started and are recorded here verbatim as given — labeled explicitly as founder-specified, not AI-inferred, so nobody mistakes them for a pragmatic call made mid-build:

- Commission 12% home cooks (configurable); mall 6% (dormant); buyer platform fee ₹0 default.
- Seller delivery fee is the seller's money, commission on items only.
- Platform delivery only for orders ≥ ₹250 by default (config), fee fully passed through.
- Pilot cohort FSSAI facilitation sponsored at ₹2,000/seller, capped at 10 sellers via config.
- Mall Mode single-store code retained but flagged off; order-group rework deferred until a mall partner is signed.

*(Implementation note: commission/fee defaults above already match `DEFAULTS` in `src/lib/config.ts` from the original build — `commissionHomePct: 12`, `commissionMallPct: 6`, `platformFeePaise: 0` — so no schema/config change was needed to satisfy them in Phase 1. The delivery-fee-ownership, ≥₹250 platform-delivery threshold, FSSAI sponsorship cap, and Mall Mode deferral are fulfillment-pivot / GST / Mall Mode items that land in later phases per the phase plan; Phase 1 scope was security & production hardening only, so none of this list required a code change this phase — it's recorded now so later phases build against the founder's actual wording, not a paraphrase.)*

## Pilot Hardening v2 — Phase 1 (Security & production hardening)

27. **Startup env validation lives in `src/instrumentation.ts` + `src/lib/env.ts` (zod).** Next 14.2's `instrumentationHook` is still experimental — enabled via `next.config.mjs`'s `experimental.instrumentationHook: true`. `register()` runs once when the server boots (both `next dev` and `next start`; NOT `next build`, so it never blocks a build) and validates: `JWT_SECRET` required, min 20 chars; `MOCK_MODE` must be exactly `'true'`/`'false'` if set at all; `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`/`RAZORPAY_WEBHOOK_SECRET` required only when `MOCK_MODE=false`. `DATABASE_URL` is deliberately NOT required — the documented zero-setup dev path (embedded PGlite) stays valid without it.
28. **`register()` calls `process.exit(1)` on validation failure, not just throw.** Verified empirically: Next.js's own handling of a thrown instrumentation error does NOT crash the `next start` process — it leaves the HTTP server bound to its port, failing every request with a 500 forever (confirmed by running it: the port stays open, every request logs "Failed to prepare server... Environment validation failed"). That's not "refuses to start" per this phase's hard requirement, so `register()` catches the throw and exits the process itself — confirmed the port never opens and the process exits with code 1 when `JWT_SECRET` is missing/short, and starts and serves normally (200s) once it's set correctly.
29. **`JWT_SECRET` fallback removed** from `src/lib/auth/index.ts`'s `jwtSecret()` — it now throws directly if unset, as defense-in-depth independent of whether instrumentation.ts is correctly wired for a given deployment target (defensive redundancy, not reliance on a single guard).
30. **Rate limiting is a hand-rolled in-memory token bucket** (`src/lib/rate-limit.ts`), explicitly single-instance scope per the phase brief (no Redis/queue infra exists anywhere else in this app either — consistent with the original build's "no background jobs, no Docker, no workers" stance). Applied to: `POST /api/auth/login` (10 req / 5 min, keyed by IP — pre-auth, no account to key on yet), `POST /api/auth/register` (5 / 10 min, keyed by IP), `POST /api/orders` (20 / 5 min, keyed by **account**, not IP — a single gated-society Wi-Fi/NAT gateway can front 200-500 households, so an IP-keyed limit here would throttle unrelated neighbours together), `POST /api/orders/[id]/verify-otp` (8 / 10 min, keyed by **order id + account** — a 4-digit OTP is only 10,000 combinations, worth throttling hard; not a global per-account limit so guessing one order's OTP can't be used to lock a buyer out of verifying a different order).
31. **10 km radius filter moved into SQL** (`src/lib/browse.ts`'s `browseListings`): a Haversine expression (`haversineKmSql`) runs in the query's WHERE clause against `coalesce(users.lat, societies.lat)` / `coalesce(users.lng, societies.lng)` — the same seller-point fallback the JS version always used — instead of fetching every eligible listing and filtering in a JS loop. Added btree indexes `users_lat_lng_idx` and `societies_lat_lng_idx` (migration `drizzle/0001_peaceful_true_believers.sql`, generated via `npm run db:generate` — not hand-edited). `getListingDetail()`'s distance display and the order-creation route's server-side re-validation (`src/app/api/orders/route.ts`) are deliberately left as JS `haversineKm()` calls — both are single-row distance checks, not a filter over many rows, so there's no query to push into SQL.
32. **Unit test proving the SQL boundary** (`src/lib/browse.test.ts`, run via `npm test` → `tsx --test`): builds an isolated in-memory PGlite instance (not the shared dev `.data/pglite` — nothing persists, nothing to clean up), migrates it with the real `drizzle/` migrations, injects it into the app's lazy `getDb()` singleton (`globalThis.__gharseDb`), seeds two sellers placed at *exactly* 9.9 km and 10.1 km due north of a fixed origin (an exact haversine inversion when moving due north only — no floating-point boundary flakiness), and asserts `browseListings()` includes the first and excludes the second. Deliberately tests the SQL translation end-to-end rather than re-testing `geo.ts`'s already-correct JS formula in isolation. No new test framework dependency — Node's built-in `node:test` + the `tsx` already used for `db:seed`, run via one explicit file path (`npm test` targets `src/lib/browse.test.ts` directly rather than a glob, since Node's default test-file discovery doesn't reliably pick up `.ts` files); revisit if/when more test files are added.
33. **`public/sw.js` is now a generated build artifact**, gitignored; `public/sw.template.js` (tracked) is the source of truth. `scripts/gen-sw.mjs` runs automatically before every build (`"prebuild"` npm script, npm's own pre-script convention — no new tooling) and stamps the cache name from `package.json`'s `version` plus a build id (`SOURCE_VERSION`/`REPL_DEPLOYMENT_ID`/`GITHUB_SHA`/`VERCEL_GIT_COMMIT_SHA` if the host sets one, else `Date.now()`), so every deploy gets a distinct cache name and `activate()` sweeps every older one automatically.
34. **Service worker fetch strategy changed**: navigations and `/api/*` **GET** requests are now network-first with a cache fallback (previously `/api/*` was network-only, never cached — see original decision #3). This supersedes that decision's "never caches `/api/*`" line, scoped deliberately: only GET responses are ever considered (the fetch handler already returns immediately for any non-GET method, so orders/payments POSTs are untouched either way), and the network is always tried first — the cached copy is only served when the network is unreachable, so online behaviour is unchanged and an offline visitor gets a last-known-good response instead of a hard failure. Static assets + remote images stay cache-first (instant repeat loads; a new deploy's cache-bust is what picks up changes, not per-request revalidation).
35. **"Update available — reload" is a dedicated persistent banner** (`src/components/sw-register.tsx`), not the existing `useToast()` system (`src/components/providers.tsx`). The existing toast auto-dismisses after ~2.8s and has no slot for an action button; this prompt needs to stay on screen until clicked and needs a "Reload" button, so it's its own small fixed-position component reusing the app's existing color tokens (`bg-ink`/`bg-leaf`, `rounded-card`, `shadow-lift`) rather than repurposing a component built for a different job.
36. **Secrets audit found nothing to rotate.** `git log --all -p -- .env` is empty, `.env` is (and always was) gitignored, and the only tracked `JWT_SECRET` string is `.env.example`'s placeholder value — not a real credential. Documented in the new `SECURITY.md` alongside rotation steps for every secret this app uses and a Replit Secrets-panel reminder, per this phase's requirement (with a rotation instruction ready to go, in case that audit result ever changes).

## Pilot Hardening v2 — Phase 2 (Fulfillment model)

37. **Schema additions beyond the phase brief's own list.** `orders.gstInPaise` (integer, default 0) was added even though the brief's schema section didn't itemize it, because the bill-breakup requirement ("Items, Delivery, Platform fee, GST 5% on food, Total") needs the GST amount persisted the same way every other bill component already is (`subtotalInPaise`/`deliveryFeeInPaise`/`platformFeeInPaise`/`commissionInPaise` are all stored columns, not values re-derived from a possibly-changing rate) — trusting a client-recomputed number for money already charged would be inconsistent with that pattern. `sellerProfiles.sellerDeliveryRadiusKm` defaults to 5 km (not specified in the brief) — half the platform's 10 km hyperlocal radius, a pragmatic starting point admins/sellers can tune.
38. **`buyerPlatformFeeInPaise` (from the brief's platform_config list) maps onto the already-existing `platformFeePaise` config key** — same semantics (generic per-order buyer fee, default ₹0, admin-editable via `/admin/settings`), not duplicated under a new name. Avoids two competing "buyer fee" concepts and leaves the existing admin settings API/UI it's already wired into unchanged.
39. **`platformDeliveryMinOrderPaise` added to `platform_config`** (default 25000 = ₹250) even though it wasn't itemized in this phase's own three-field platform_config list — it implements the founder-specified "platform delivery only for orders ≥ ₹250 by default (config)" decision from DECISIONS.md's Founder-Specified section, which explicitly named "later phases" as its home; this is that phase. Without it, "platform-facilitated" couldn't be gated as specified.
40. **`platformDeliveryFeeInPaise` is wired as `getBestQuote()`'s own fallback-quote amount** in `src/lib/delivery/orchestrator.ts` (replacing its previous hardcoded `4900` literal), not a separate, disconnected admin field — matches the founder's "fee fully passed through": the buyer is always quoted whatever `getBestQuote()` actually returns, whether that's a live/mock provider quote or this configured floor when every provider is down/disabled. `platform_config` gained its first boolean-valued setting (`platformDeliveryEnabled`) — added a `bool()` helper in `src/lib/db/platform.ts` alongside the existing `num()` helper (values still stored as `'true'`/`'false'` text, consistent with the table's text-value design).
41. **GST 5% applies only to home-kitchen orders** (`orders.type === 'home_delivery'`), matching the global brief's "GST on home-food orders" wording — mall/restaurant orders (`mall_pickup`) keep `gstInPaise = 0`, consistent with Mall Mode being deferred this pilot. The rate itself (`DEFAULTS.gstPct = 5`) is a hardcoded constant, **not** a `platform_config` admin setting — it's a statutory rate under Sec 9(5) CGST, not a pricing lever admins should be able to casually retune from a settings screen. Bill-facing copy is worded as GharSe's own tax posture ("GharSe is the deemed supplier… the kitchen doesn't need its own GST registration for this"), not a claim of any government API integration.
42. **Self-pickup orders skip the buyer-address / 10 km hyperlocal-radius check entirely** — no address is collected at all, since the radius rule exists to bound a *delivery* leg and self-pickup has none. Seller-delivery is checked against **both** the platform's 10 km radius **and** the seller's own `sellerDeliveryRadiusKm` (the tighter of the two wins in practice, since sellers default to 5 km); platform-delivery is checked against the platform radius only (as before) plus the new minimum-order threshold.
43. **`maxOrdersPerSlot` is a seller-level cap on in-flight orders per meal-time window**, not a per-dish limit — new `src/lib/slots.ts` defines fixed hour-of-day windows (breakfast 6–11, lunch 11–16, dinner 18–23, server-local time, no timezone handling — consistent with the rest of the app never doing timezone conversion) and counts non-cancelled/non-refunded orders created inside the current window. Computed lazily at browse-time and order-creation time, no cron/workers — same "compute it when someone looks" philosophy as the FSSAI pending-grace window and delivery tracking sync. Outside every serving window, nothing is blocked on this basis (deliberately not a store-hours gate). Enforced in three places: `browseListings()` and `getListingDetail()` (buyer sees "Sold out for this slot" and the Add button is disabled) and `POST /api/orders` (hard server-side reject — the UI gate alone wouldn't be enough, matching this app's existing pattern of re-validating client-supplied state server-side, e.g. the 10 km radius).
44. **The OTP handshake (`/api/orders/[id]/verify-otp`) now branches on `fulfillmentType` instead of `order.type`**: `self_pickup` (home kitchen *or* mall counter) always goes `ready`→`picked_up`; `seller_delivery` and `platform_delivery` both go `out_for_delivery`→`delivered`. This let mall pickup's existing counter-pickup flow fall out of the same code path as home self-pickup for free — mall orders keep `fulfillmentType`'s DB default of `'self_pickup'` (never explicitly set in the `mall_pickup` order-creation branch) rather than needing a third branch.
45. **Added a new order-status action, `out_for_delivery`, gated to `fulfillmentType === 'seller_delivery'` only.** It's the seller's manual "I'm on my way" step since there's no third-party rider or tracking for that leg; `platform_delivery` orders reach the same order status automatically via the orchestrator's existing tracking-sync polling (unchanged), and `self_pickup` never uses it at all (guarded with an explicit 400 if attempted).
46. **Fixed a regression the fulfillment pivot would otherwise silently introduce**: `/api/seller/earnings` and `/api/seller/summary`'s "today" stats previously counted only `status === 'delivered'` as a completed order — correct back when every seller-owned order ended that way (home delivery via rider). Self-pickup orders now terminate at `'picked_up'` instead, so both routes were updated to count `status IN ('delivered', 'picked_up')`, matching the pattern `/api/admin/summary`'s GMV/commission totals already used.
47. **`/api/quote` was reshaped to accept optional `lat`/`lng`** (previously required) so it can return a seller's self-pickup/seller-delivery/platform-delivery offer flags and pickup instructions *before* the buyer has set a location — self-pickup, the new default, needs no address at all. It's the only consumer of this endpoint (`checkout-client.tsx`), so the response shape was freely redesigned rather than versioned or kept backward-compatible.
48. **Seller-facing fulfillment settings live at a new `/seller/fulfillment` page + `/api/seller/fulfillment` route** (GET/PATCH), not folded into the existing compliance or listings pages — it's a distinct concern (how orders reach the buyer, not what's cooked or whether the kitchen is licensed), matching the app's existing one-page-per-concern layout (listings / compliance / earnings are already separate). The PATCH requires at least one of `offersSelfPickup`/`offersSellerDelivery` to stay true — a seller can't disable every fulfillment option.
49. **`FEATURE_MALL_MODE` flag was intentionally NOT implemented this phase.** The global brief lists it as a hard constraint but Phase 1 explicitly left it "fully open for whichever phase owns it," and this phase's own scope section (schema / checkout / seller side / keep the orchestrator working) doesn't mention it. Mall Mode's existing code path was kept fully working and untouched (verified via a live `/m/[mallSlug]` render and reasoning through both changed shared routes — `status` and `verify-otp` — which mall orders fall through unaffected, since `fulfillmentType` defaults to `self_pickup` for them). The flag itself remains for a later phase to add.
50. **TDS u/s 194-O tracking, real Razorpay Route payouts, and the admin T+2 manual-payout batch tool were not touched this phase** — "merchant of record" plumbing beyond the GST bill-breakup line this phase's brief explicitly asked for stays fully open, per the global brief's phase-plan framing (item 2 of the three strategic changes is broader than this phase's fulfillment-model scope).

## Pilot Hardening v2 — Phase 3 (Money: invoices, payouts, tax)

51. **`payoutId` lives directly on `orders`** (nullable FK to a new `payouts` table), not a separate join table. A batch groups many orders into one payout row per seller; tagging each swept order with the payout it landed in is enough to (a) know what's already been paid out and (b) make batch generation idempotent — re-running "Generate T+2 batch" only ever sees orders where `payoutId IS NULL`. Matches the codebase's existing preference for a direct FK over a join table (e.g. `reviews.orderId`, `deliveries.orderId`) when the relationship is one-to-many, not many-to-many. New tables: `payouts` (sellerId, periodStart/End, orderCount, grossSalesInPaise, commissionInPaise, gatewayFeeEstimateInPaise, tds194OInPaise, netPayableInPaise, status pending|paid, paidAt, utrReference, payoutDestinationSnapshot) and `seller_fy_payout_totals` (sellerId + fyLabel unique, grossPayoutInPaise) for the Sec 194-O threshold. Migration `drizzle/0003_panoramic_big_bertha.sql`, via `npm run db:generate` as always.
52. **A payout's `commissionInPaise` is the sum of each included order's own already-stored `commissionInPaise`**, not a fresh recomputation against today's `commissionHomePct`. The brief's "commission (12% default, admin-editable)" is satisfied by the rate already being admin-editable at order time (`/admin/settings`) — summing the historical per-order values means a later rate change can never retroactively rewrite what an already-placed order actually owed. Same reasoning as #38's "don't duplicate an existing admin-editable concept."
53. **`gatewayFeeEstimatePct` (2%) and the Sec 194-O constants (`tds194OPct` 0.1%, `tds194OThresholdPaise` ₹5,00,000) live as fixed `DEFAULTS` in `src/lib/config.ts`, not `platform_config`.** The brief describes the commission rate as "admin-editable" but doesn't say that for the gateway-fee estimate or the TDS rate/threshold — the former is an internal accounting estimate (real Razorpay fees vary by payment method and aren't something an admin should casually retune expecting it to change actual bank costs), the latter is a statutory rate/threshold, same treatment as `gstPct` (#41).
54. **TDS 194-O crossing is an all-or-nothing-per-batch approximation, not a precise pro-rated split of the exact rupee that crosses ₹5,00,000.** `generatePayoutBatch()` adds this batch's gross sales to the seller's running FY total (`seller_fy_payout_totals`, keyed by an Indian Apr–Mar `fyLabel()` e.g. "2026-27"); if the *new* cumulative total exceeds the threshold, TDS applies to the *entire current batch's* gross sales, not just the portion above the line. Documented simplification, verified against a synthetic ₹6,00,000 single-order batch (correctly produced ₹600 TDS = 0.1% of the full amount) — reasonable at pilot scale (a handful of home cooks, each batch easy to eyeball before an actual bank transfer) but should be tightened to a precise threshold-crossing split before scaling to sellers who routinely straddle the line mid-batch.
55. **No "batch ID" grouping concept — a payout row's own `status` (`pending`/`paid`) is what the CSV export and the "needs a transfer" view key off.** "Generate T+2 batch" just inserts however many per-seller `payouts` rows are newly eligible; the CSV export (`/api/admin/payouts/export`) always exports every currently-`pending` row, which is exactly "everything that still needs a manual bank/UPI transfer" — clicking "Generate" again later just adds more pending rows as more orders cross 48h, no separate run/batch identifier needed.
56. **`payoutDestinationSnapshot` freezes `seller_profiles.payoutVpaOrBank` at batch-generation time** onto the payout row itself, rather than the CSV/admin view live-joining `seller_profiles` every time. If a seller updates their UPI ID after a batch is generated but before it's paid, the historical record of what was actually paid-to stays accurate and auditable.
57. **Verified the money math end-to-end against the live dev DB** (`.data/pglite`, discarded afterward) rather than trusting it from reading the code: ran `generatePayoutBatch()` against the real seed data (12% commission, 2% gateway fee correctly derived), confirmed a second run sweeps zero orders (idempotency via `payoutId`), and inserted a synthetic ₹6,00,000 single order for a seller with no prior FY total to confirm the TDS crossing logic fires correctly (₹600 = 0.1%) — see #54. No permanent test file was added for this (unlike `browse.test.ts`'s SQL-boundary test) since it's pure application logic over already-fetched rows, not a SQL translation to verify; `npm test` and `npm run build` both still pass unchanged.
58. **Invoices are issued in the platform's name, not the cook's** — `BRAND.gstin`/`BRAND.registeredAddress` (new fields in `src/lib/config.ts`) are explicit placeholder strings (`'GSTIN-PENDING-REGISTRATION'` etc.) with an inline comment to replace them before a real pilot launch; the invoice page also surfaces a footnote whenever the GSTIN string contains "PENDING". This is deliberate: GharSe is the deemed supplier under Sec 9(5) CGST for home-food orders, so the tax invoice must carry the platform's registration, not the kitchen's — the kitchen is shown separately as "Fulfilled by" for the buyer's reference only.
59. **CGST/SGST is modeled as an even 2.5%/2.5% split of the stored 5% `gstInPaise`, assuming an intra-state supply** — reasonable for a single Hyderabad society pilot where buyer and platform are in the same state, but explicitly worded as guidance ("assuming an intra-state supply... verify... with your CA") rather than a filed determination, since an inter-state edge case would actually need IGST instead. Orders with `gstInPaise === 0` (today, only `mall_pickup` — Mall Mode is deferred anyway) render as a plain "Bill" with no tax lines instead of a "Tax Invoice", so the document never asserts a GST treatment that wasn't actually applied to that order.
60. **Invoice access reuses `GET /api/orders/[id]`'s exact authorization logic** (buyer, the order's seller, the restaurant's manager, or admin) rather than inventing a new rule, and the "View invoice" link on the buyer's order page is gated on `order.status !== 'placed'` (i.e. payment has at least been initiated/captured) — mirrors how the existing OTP-reveal logic on that same page already gates on order state rather than introducing a new payment-status field to thread through the client.
61. **`settlements.ts` (Razorpay Route) gained a "when to enable" README block** per this phase's explicit instruction, listing three preconditions (Route/linked-accounts approved for this business, volume that makes manual transfers a real burden, and TDS/GST reconciled against per-transfer settlement rather than this phase's batch-ledger model) — the interface itself is untouched; the manual T+2 admin batch tool (`src/lib/payouts.ts`, `/admin/payouts`) is the pilot's real payout mechanism.

## Pilot Hardening v2 — Phase 4 (Compliance center refinements)

62. **FSSAI Basic Registration is now the default recommendation everywhere** (wizard step 3's radio default and copy, `fssaiApplications.licenseType`'s DB column default flipped `state` → `registration` via migration `drizzle/0004_left_union_jack.sql`, the compliance page's static footnote, and the new `/legal/food-safety` bullet) — turnover ≤ ₹1.5 crore, rule effective 1 April 2026, per this phase's brief. Every surface pairs it with the same "some categories require a State License — confirm your Kind of Business on FoSCoS" note and explicitly declines to assert either tier as definitive, matching the brief's own wording almost verbatim rather than paraphrasing it into something stronger.
63. **New `fssaiFilingModeEnum` (`'facilitator' | 'self'`) plus `fssaiApplications.filingMode`/`facilitationCostInPaise`/`sponsoredByPlatform`** (same migration as #62). `filingMode` is the seller's choice on a new wizard step 5 ("How do you want to file?"), sent through on `POST /api/fssai/applications`. `'facilitator'` reproduces exactly what already existed pre-Phase-4 (status starts `submitted_to_backoffice`, admins get notified, `facilitationCostInPaise` = ₹2,000, `sponsoredByPlatform` computed against the cohort cap — see #64). `'self'` is new: status starts `draft`, **no** back-office task and **no** admin notification are created (the brief's own distinction — "File it for me" creates a back-office task; "I'll file myself" does not), and `facilitationCostInPaise`/`sponsoredByPlatform` are forced to `0`/`false` since GharSe does no facilitation work on a self-filed application — there is nothing to record as an acquisition cost.
64. **Self-filers can self-report their FoSCoS reference number** via a new seller-only `PATCH /api/fssai/applications/[id]` (distinct from the existing admin-only `PATCH /api/admin/fssai/[id]`), gated to `filingMode === 'self' && status === 'draft'` and ownership by the requesting seller. It moves the application to `filed_on_foscos` with the entered ref (mirroring admin's own `'file'` action), notifies admins so they know to track a self-filed application through to grant, and lets `/seller/compliance`'s existing pending-application UI (timeline, grace-window countdown) keep working unmodified for both filing paths. Granting the final license number stays admin-only either way — unchanged from the pre-existing verification-by-admin model, since a self-reported "granted" status without any check would be a real compliance risk the brief never asked to introduce.
65. **`GET /api/admin/fssai` now excludes `status = 'draft'` rows** (a plain `ne()` filter) — the page is literally titled "FSSAI back-office queue," and a self-filed draft has no back-office task attached to it yet; it only enters admin's view once the seller self-files (→ `filed_on_foscos`), at which point it needs the same "track to grant" attention a facilitator-filed application gets. `GET /api/admin/summary`'s `fssaiQueue` counter already only counted `submitted_to_backoffice`/`filed_on_foscos`, so it required no change to stay consistent with this.
66. **Sponsorship-cap logic**: on a `'facilitator'` submission, the route counts distinct `sellerId`s with `sponsoredByPlatform = true` across all their applications and sponsors the new one (`sponsoredByPlatform = true`) only if that count is under `platform_config.fssaiSponsorshipCapPerCohort` (new key, `DEFAULTS` default 10, admin-editable via `/admin/settings` — the founder's own "capped at 10 sellers via config" wording). A seller already sponsored on an earlier application (e.g. resubmitting after a rejection) stays sponsored regardless of the current cap count, so a cap that fills up later never un-sponsors someone retroactively. What happens to a facilitator-path application that lands outside the cap is deliberately left as just a `sponsoredByPlatform = false` flag with a "contact support" note in the UI — actually billing a seller for facilitation is a real payment flow this phase's brief never asked for ("Sponsored cost is recorded as acquisition cost, never as a seller debt" only specifies the sponsored case), so building a charge-the-seller mechanism for the unsponsored case is explicitly out of scope here.
67. **The brief's "admin toggle per society/cohort" is implemented as a per-application toggle** (`PATCH /api/admin/fssai/[id]` gained a `'sponsor'` action, exposed as a "Toggle" link next to each facilitator-path row in `/admin/fssai`) rather than a society- or cohort-scoped setting. The pilot has exactly one society and one cohort (all pilot sellers), so a per-application toggle and a per-cohort toggle are behaviourally identical at this scale; building a real multi-cohort config UI for a single-society pilot would be speculative scope. Recorded here explicitly so a future multi-society phase knows this was a deliberate simplification, not an oversight.
68. **The wizard's actual deliverable — "a prefilled application summary PDF/HTML + document bundle" — is a new printable page**, `/fssai/[id]/summary` (+ `GET /api/fssai/applications/[id]/summary`), styled after Phase 3's tax-invoice page (`window.print()`, same letterhead/Card pattern) rather than generating an actual PDF file — no PDF library exists anywhere in this codebase, and the browser's print-to-PDF is exactly how the invoice already solves the identical "give me a document" need, so introducing a new dependency for this would be inconsistent with the app's existing approach. It shows applicant/kitchen details, the license-type recommendation note, the document bundle (same pill-link rendering the admin FSSAI queue already used), and then branches: facilitator-path shows the facilitation cost/sponsorship line; self-path shows a numbered step-by-step FoSCoS walkthrough with a real link to `https://foscos.fssai.gov.in/` (the actual public portal — not a fake submission endpoint) plus the self-file ref-number form from #64. The same page is linked from both `/seller/compliance` (seller) and `/admin/fssai` (admin/facilitator) — one shared source document for whoever actually does the filing, matching the brief's "the seller or a facilitator files on FoSCoS" wording.
69. **New platform-level admin setting `platformFssaiCentralLicenseNo`** (`platform_config`, text, default `''`) — validated on `PATCH /api/admin/settings` as either blank or a 14-digit number (same shape as every other FSSAI number in this codebase), added to a new `EDITABLE_TEXT` set alongside the existing numeric/boolean editable sets rather than overloading either. `src/app/admin/layout.tsx` now fetches platform settings server-side and renders a persistent chili-toned banner (linking to Settings) on **every** `/admin/*` page whenever it's empty — deliberately placed in the shared layout, not just the settings page, since the brief calls it an "admin banner" (implying platform-wide visibility) and a compliance gate this important shouldn't be discoverable only by an admin who happens to already be on the Settings tab.
70. **`POST /api/orders` now hard-blocks (503) when `!isMockMode() && !platformFssaiCentralLicenseNo`**, checked once up front for both `home_delivery` and `mall_pickup` before either branch runs. `MOCK_MODE` stays the master switch exactly as established in Phase 1 (`src/lib/env.ts`) — this new gate is fully dormant for the pilot's default `MOCK_MODE=true` and only bites the moment someone actually flips to live mode without having entered the platform's real Central FSSAI e-commerce license, which is precisely the brief's "block MOCK_MODE=false order creation" requirement.
71. **`/legal/food-safety` was made a small async server component** (it already sat under a `force-dynamic` layout, so no new `dynamic` export was needed) so its "Platform FSSAI license: applied for" line reflects the live `platformFssaiCentralLicenseNo` setting instead of being a permanently-static claim — minor scope-adjacent cleanup done while already touching FSSAI-related copy this phase, since leaving a hardcoded "applied for" string next to a brand-new admin field that tracks the real answer would immediately be a stale/contradictory pair of sources.
72. **Seed data**: explicitly set `filingMode: 'facilitator'`, `facilitationCostInPaise: 200000`, `sponsoredByPlatform: true` on both pre-existing seeded FSSAI applications (they already read as back-office-filed in their timelines, so this is just making the existing implicit state explicit, matching this codebase's general seed-file style of spelling out fields rather than leaning on defaults). Added `platformConfig` row `fssaiSponsorshipCapPerCohort: '10'` for the same reason. Deliberately did **not** seed a value for `platformFssaiCentralLicenseNo`, so the new admin banner and the live-order block are both visible out of the box — the empty state is the pilot's actual real-world starting point (no license entered yet), and demonstrating that gate working is more useful than hiding it behind a seeded fake license number.
