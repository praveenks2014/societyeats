# DECISIONS.md — assumptions & pragmatic choices

> **Rename note (Phase 1 Pilot):** the product was previously called "GharSe" (a name that belongs to another entity). It is now **PadosiPlate**; all historical decisions below have been mechanically re-worded to the new name. The brand lives in `src/config/brand.ts`.

Every non-obvious call made while building PadosiPlate in one session, and why.

## Stack & infrastructure

1. **PGlite dev fallback.** The spec mandates Postgres via `DATABASE_URL` (kept as the primary path, used on Replit). When the variable is unset, the app falls back to an embedded PGlite (WASM Postgres) at `./.data/pglite` with auto-migrate + auto-seed. Rationale: the build machine and fresh clones have no Postgres, and "fully clickable tonight" beats "install a database first". Same Drizzle API both ways; no native binaries either way.
2. **(Superseded in Phase 1 Pilot — `src/proxy.ts` now exists, see below.)** Role checks live in layouts (`/seller`, `/admin`, `/restaurant`) and in every API handler via `requireSession(roles)`. Simpler than edge middleware and avoids edge-runtime DB access.
3. **Hand-rolled service worker** instead of `@ducanh2912/next-pwa`: fewer build-time moving parts, and the spec explicitly allowed it. It precaches an offline shell, uses network-first for navigations, SWR for images, and never caches `/api/*`.
4. **SVG PWA icons.** Chrome accepts SVG manifest icons; shipping raster PNGs would need an image toolchain. Swap in PNGs later if older Android install banners matter.
5. **`.replit` committed** so "Import from GitHub" runs with zero changes (dev run + autoscale deployment config).

## Product behaviour

6. **Single-vendor basket** (like Swiggy): a cart holds items from one kitchen/counter at a time; adding from another prompts "start a new basket?". Keeps delivery quotes, commission math, and seller queues coherent.
7. **Dispatch happens at "Mark ready"**, not at accept — closest to how food actually meets riders, and it makes the chaos-toggle demo a single button press.
8. **Mock tracking is clock-derived** (dispatch timestamp encoded in the mock provider order id): rider assigned <1 min, picked up 1–3 min, in transit afterwards, then "arrived — share OTP". No timers, no workers, survives serverless restarts.
9. **Delivery quotes are deterministic** in mock (distance-based, per-provider pricing personality, clamped ₹30–₹70) so the checkout preview and the charged amount always agree. The ~15% simulated failure applies to `createDelivery` only.
10. **Order cannot be delivered without the OTP**; in mock, the buyer's tracking screen hosts the simulated "rider handset" input. Mall pickups verify the OTP from the restaurant console instead.
11. **Rejecting a paid order → `refund_pending`** and the payment row flips to `refunded` immediately in mock; live mode would call Razorpay's refund API (stub noted in code).
12. **Ratings aggregate on seller profiles** (running average + count) and only home-kitchen orders affect them; mall counters keep FSSAI display but no rating field (out of scope).
13. **Buyer location is client-held** (localStorage) and sent as query params; the server re-validates the 10 km rule at quote time *and* order time from the address coordinates, so the radius cannot be spoofed by skipping the UI.
14. **FSSAI-pending grace window**: enforced lazily at browse time (no cron) — when a pending kitchen's newest application is older than `fssaiPendingMaxDays`, its listings are set inactive during the next browse query.
15. **Admin "grant" sets a 1-year expiry** from the grant date (typical minimum FSSAI validity) since the real certificate isn't parsed.

## Integrations

16. **Live API shapes are best-effort from public docs** (Porter UAT gateway, Shadowfax Flash, Borzo business API 1.6, Surepass FSSAI) and every live branch is marked `// VERIFY against partner docs when keys arrive`. None execute in MOCK_MODE.
17. **Razorpay capture is idempotent and race-safe**: the client-side signature verify handler and the webhook both funnel into `markOrderPaid`, which no-ops unless the order is still `placed`.
18. **Settlements (Razorpay Route)** are Phase 2: interface stubbed in `src/lib/payments/settlements.ts`, earnings page shows the "T+1 via Razorpay Route — coming soon" ledger note.
19. **Notifications are in-app only** (bell + 25s polling + toasts). Web push needs VAPID keys and a push service; the `notify()` helper is the single seam where push/MSG91 SMS would plug in.
20. **Uploads go to `/public/uploads`** with type/size validation; README flags the swap to object storage for production. Seeded FSSAI "documents" reference a committed placeholder SVG so the admin queue renders without uploads.

## Data & seed

21. **Society coordinates are approximate** (Nallagandla ↔ Narsingi ≈ 8.9 km apart) so cross-society browsing sits just inside the 10 km radius — deliberately, to demo distance chips both near and far. GVK One (Banjara Hills) is ~15 km from both, keeping mall counters out of home-delivery browse.
22. **Unsplash photo IDs are best-effort**; every image renders through a `FoodImage` component that falls back to a brand-styled placeholder on 404, so a dead URL never breaks the UI.
23. **Money is integer paise everywhere**; display formatting is `en-IN`.
24. **Demo login phone numbers** follow the spec's "demo accounts" intent: buyer 9999999901, seller 9999999902, restaurant 9999999903, admin 9999999904 (password `demo1234`), plus five more sellers and two more restaurant managers on 99999999xx.

## Schema extensions beyond the spec

25. Added `order_events` (timeline), `notifications`, `ratingCount` on seller profiles, `priority` + `chaosForceFail` on `provider_health`, and `titleSnapshot` on order items (order history survives listing edits). All additive.
26. `orders.status` gained `delivery_unassigned` (spec §7.3 requires the state; the enum in §5 didn't list it).

## Pilot Hardening v2 — Founder-Specified Fixed Decisions

- Seller delivery fee is the seller's money, commission on items only.

## Pilot Hardening v2 — Phase 1 (Security & production hardening)

27. **Startup env validation lives in `src/instrumentation.ts` + `src/lib/env.ts` (zod).** Next 14.2's `instrumentationHook` is still experimental — enabled via `next.config.mjs`'s `experimental.instrumentationHook: true`. `register()` runs once when the server boots (both `next dev` and `next start`; NOT `next build`, so it never blocks a build) and validates: `JWT_SECRET` required, min 20 chars; `MOCK_MODE` must be exactly `'true'`/`'false'` if set at all; `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`/`RAZORPAY_WEBHOOK_SECRET` required only when `MOCK_MODE=false`. `DATABASE_URL` is deliberately NOT required — the documented zero-setup dev path (embedded PGlite) stays valid without it.
28. **`register()` calls `process.exit(1)` on validation failure, not just throw.** Verified empirically: Next.js's own handling of a thrown instrumentation error does NOT crash the `next start` process — it leaves the HTTP server bound to its port, failing every request with a 500 forever (confirmed by running it: the port stays open, every request logs "Failed to prepare server... Environment validation failed"). That's not "refuses to start" per this phase's hard requirement, so `register()` catches the throw and exits the process itself — confirmed the port never opens and the process exits with code 1 when `JWT_SECRET` is missing/short, and starts and serves normally (200s) once it's set correctly.
29. **`JWT_SECRET` fallback removed** from `src/lib/auth/index.ts`'s `jwtSecret()` — it now throws directly if unset, as defense-in-depth independent of whether instrumentation.ts is correctly wired for a given deployment target (defensive redundancy, not reliance on a single guard).
30. **Rate limiting is a hand-rolled in-memory token bucket** (`src/lib/rate-limit.ts`), explicitly single-instance scope per the phase brief (no Redis/queue infra exists anywhere else in this app either — consistent with the original build's "no background jobs, no Docker, no workers" stance). Applied to: `POST /api/auth/login` (10 req / 5 min, keyed by IP — pre-auth, no account to key on yet), `POST /api/auth/register` (5 / 10 min, keyed by IP), `POST /api/orders` (20 / 5 min, keyed by **account**, not IP — a single gated-society Wi-Fi/NAT gateway can front 200-500 households, so an IP-keyed limit here would throttle unrelated neighbours together), `POST /api/orders/[id]/verify-otp` (8 / 10 min, keyed by **order id + account** — a 4-digit OTP is only 10,000 combinations, worth throttling hard; not a global per-account limit so guessing one order's OTP can't be used to lock a buyer out of verifying a different order).
31. **10 km radius filter moved into SQL** (`src/lib/browse.ts`'s `browseListings`): a Haversine expression (`haversineKmSql`) runs in the query's WHERE clause against `coalesce(users.lat, societies.lat)` / `coalesce(users.lng, societies.lng)` — the same seller-point fallback the JS version always used — instead of fetching every eligible listing and filtering in a JS loop. Added btree indexes `users_lat_lng_idx` and `societies_lat_lng_idx` (migration `drizzle/0001_peaceful_true_believers.sql`, generated via `npm run db:generate` — not hand-edited). `getListingDetail()`'s distance display and the order-creation route's server-side re-validation (`src/app/api/orders/route.ts`) are deliberately left as JS `haversineKm()` calls — both are single-row distance checks, not a filter over many rows, so there's no query to push into SQL.
32. **Unit test proving the SQL boundary** (`src/lib/browse.test.ts`, run via `npm test` → `tsx --test`): builds an isolated in-memory PGlite instance (not the shared dev `.data/pglite` — nothing persists, nothing to clean up), migrates it with the real `drizzle/` migrations, injects it into the app's lazy `getDb()` singleton (`globalThis.__padosiDb`), seeds two sellers placed at *exactly* 9.9 km and 10.1 km due north of a fixed origin (an exact haversine inversion when moving due north only — no floating-point boundary flakiness), and asserts `browseListings()` includes the first and excludes the second. Deliberately tests the SQL translation end-to-end rather than re-testing `geo.ts`'s already-correct JS formula in isolation. No new test framework dependency — Node's built-in `node:test` + the `tsx` already used for `db:seed`, run via one explicit file path (`npm test` targets `src/lib/browse.test.ts` directly rather than a glob, since Node's default test-file discovery doesn't reliably pick up `.ts` files); revisit if/when more test files are added.
33. **`public/sw.js` is now a generated build artifact**, gitignored; `public/sw.template.js` (tracked) is the source of truth. `scripts/gen-sw.mjs` runs automatically before every build (`"prebuild"` npm script, npm's own pre-script convention — no new tooling) and stamps the cache name from `package.json`'s `version` plus a build id (`SOURCE_VERSION`/`REPL_DEPLOYMENT_ID`/`GITHUB_SHA`/`VERCEL_GIT_COMMIT_SHA` if the host sets one, else `Date.now()`), so every deploy gets a distinct cache name and `activate()` sweeps every older one automatically.
34. **Service worker fetch strategy changed**: navigations and `/api/*` **GET** requests are now network-first with a cache fallback (previously `/api/*` was network-only, never cached — see original decision #3). This supersedes that decision's "never caches `/api/*`" line, scoped deliberately: only GET responses are ever considered (the fetch handler already returns immediately for any non-GET method, so orders/payments POSTs are untouched either way), and the network is always tried first — the cached copy is only served when the network is unreachable, so online behaviour is unchanged and an offline visitor gets a last-known-good response instead of a hard failure. Static assets + remote images stay cache-first (instant repeat loads; a new deploy's cache-bust is what picks up changes, not per-request revalidation).
35. **"Update available — reload" is a dedicated persistent banner** (`src/components/sw-register.tsx`), not the existing `useToast()` system (`src/components/providers.tsx`). The existing toast auto-dismisses after ~2.8s and has no slot for an action button; this prompt needs to stay on screen until clicked and needs a "Reload" button, so it's its own small fixed-position component reusing the app's existing color tokens (`bg-ink`/`bg-leaf`, `rounded-card`, `shadow-lift`) rather than repurposing a component built for a different job.
36. **Secrets audit found nothing to rotate.** `git log --all -p -- .env` is empty, `.env` is (and always was) gitignored, and the only tracked `JWT_SECRET` string is `.env.example`'s placeholder value — not a real credential. Documented in the new `SECURITY.md` alongside rotation steps for every secret this app uses and a Replit Secrets-panel reminder, per this phase's requirement (with a rotation instruction ready to go, in case that audit result ever changes).

## Pilot Hardening v2 — Phase 2 (Fulfillment model)

37. **Schema additions beyond the phase brief's own list.** `orders.gstInPaise` (integer, default 0) was added even though the brief's schema section didn't itemize it, because the bill-breakup requirement ("Items, Delivery, Platform fee, GST 5% on food, Total") needs the GST amount persisted the same way every other bill component already is (`subtotalInPaise`/`deliveryFeeInPaise`/`platformFeeInPaise`/`commissionInPaise` are all stored columns, not values re-derived from a possibly-changing rate) — trusting a client-recomputed number for money already charged would be inconsistent with that pattern. `sellerProfiles.sellerDeliveryRadiusKm` defaults to 5 km (not specified in the brief) — half the platform's 10 km hyperlocal radius, a pragmatic starting point admins/sellers can tune.
38. **`buyerPlatformFeeInPaise` (from the brief's platform_config list) maps onto the already-existing `platformFeePaise` config key** — same semantics (generic per-order buyer fee, default ₹0, admin-editable via `/admin/settings`), not duplicated under a new name. Avoids two competing "buyer fee" concepts and leaves the existing admin settings API/UI it's already wired into unchanged.
39. **`platformDeliveryMinOrderPaise` added to `platform_config`** (default 25000 = ₹250) even though it wasn't itemized in this phase's own three-field platform_config list — it implements the founder-specified "platform delivery only for orders ≥ ₹250 by default (config)" decision from DECISIONS.md's Founder-Specified section, which explicitly named "later phases" as its home; this is that phase. Without it, "platform-facilitated" couldn't be gated as specified.
40. **`platformDeliveryFeeInPaise` is wired as `getBestQuote()`'s own fallback-quote amount** in `src/lib/delivery/orchestrator.ts` (replacing its previous hardcoded `4900` literal), not a separate, disconnected admin field — matches the founder's "fee fully passed through": the buyer is always quoted whatever `getBestQuote()` actually returns, whether that's a live/mock provider quote or this configured floor when every provider is down/disabled. `platform_config` gained its first boolean-valued setting (`platformDeliveryEnabled`) — added a `bool()` helper in `src/lib/db/platform.ts` alongside the existing `num()` helper (values still stored as `'true'`/`'false'` text, consistent with the table's text-value design).
41. **GST 5% applies only to home-kitchen orders** (`orders.type === 'home_delivery'`), matching the global brief's "GST on home-food orders" wording — mall/restaurant orders (`mall_pickup`) keep `gstInPaise = 0`, consistent with Mall Mode being deferred this pilot. The rate itself (`DEFAULTS.gstPct = 5`) is a hardcoded constant, **not** a `platform_config` admin setting — it's a statutory rate under Sec 9(5) CGST, not a pricing lever admins should be able to casually retune from a settings screen. Bill-facing copy is worded as PadosiPlate's own tax posture ("PadosiPlate is the deemed supplier… the kitchen doesn't need its own GST registration for this"), not a claim of any government API integration.
42. **Self-pickup orders skip the buyer-address / 10 km hyperlocal-radius check entirely** — no address is collected at all, since the radius rule exists to bound a *delivery* leg and self-pickup has none. Seller-delivery is checked against **both** the platform's 10 km radius **and** the seller's own `sellerDeliveryRadiusKm` (the tighter of the two wins in practice, since sellers default to 5 km); platform-delivery is checked against the platform radius only (as before) plus the new minimum-order threshold.
43. **`maxOrdersPerSlot` is a seller-level cap on in-flight orders per meal-time window**, not a per-dish limit — new `src/lib/slots.ts` defines fixed hour-of-day windows (breakfast 6–11, lunch 11–16, dinner 18–23, server-local time, no timezone handling — consistent with the rest of the app never doing timezone conversion) and counts non-cancelled/non-refunded orders created inside the current window. Computed lazily at browse-time and order-creation time, no cron/workers — same "compute it when someone looks" philosophy as the FSSAI pending-grace window and delivery tracking sync. Outside every serving window, nothing is blocked on this basis (deliberately not a store-hours gate). Enforced in three places: `browseListings()` and `getListingDetail()` (buyer sees "Sold out for this slot" and the Add button is disabled) and `POST /api/orders` (hard server-side reject — the UI gate alone wouldn't be enough, matching this app's existing pattern of re-validating client-supplied state server-side, e.g. the 10 km radius).
44. **The OTP handshake (`/api/orders/[id]/verify-otp`) now branches on `fulfillmentType` instead of `order.type`**: `self_pickup` (home kitchen *or* mall counter) always goes `ready`→`picked_up`; `seller_delivery` and `platform_delivery` both go `out_for_delivery`→`delivered`. This let mall pickup's existing counter-pickup flow fall out of the same code path as home self-pickup for free — mall orders keep `fulfillmentType`'s DB default of `'self_pickup'` (never explicitly set in the `mall_pickup` order-creation branch) rather than needing a third branch.
45. **Added a new order-status action, `out_for_delivery`, gated to `fulfillmentType === 'seller_delivery'` only.** It's the seller's manual "I'm on my way" step since there's no third-party rider or tracking for that leg; `platform_delivery` orders reach the same order status automatically via the orchestrator's existing tracking-sync polling (unchanged), and `self_pickup` never uses it at all (guarded with an explicit 400 if attempted).
46. **Fixed a regression the fulfillment pivot would otherwise silently introduce**: `/api/seller/earnings` and `/api/seller/summary`'s "today" stats previously counted only `status === 'delivered'` as a completed order — correct back when every seller-owned order ended that way (home delivery via rider). Self-pickup orders now terminate at `'picked_up'` instead, so both routes were updated to count `status IN ('delivered', 'picked_up')`, matching the pattern `/api/admin/summary`'s GMV/commission totals already used.
47. **`/api/quote` was reshaped to accept optional `lat`/`lng`** (previously required) so it can return a seller's self-pickup/seller-delivery/platform-delivery offer flags and pickup instructions *before* the buyer has set a location — self-pickup, the new default, needs no address at all. It's the only consumer of this endpoint (`checkout-client.tsx`), so the response shape was freely redesigned rather than versioned or kept backward-compatible.
48. **Seller-facing fulfillment settings live at a new `/seller/fulfillment` page + `/api/seller/fulfillment` route** (GET/PATCH), not folded into the existing compliance or listings pages — it's a distinct concern (how orders reach the buyer, not what's cooked or whether the kitchen is licensed), matching the app's existing one-page-per-concern layout (listings / compliance / earnings are already separate). The PATCH requires at least one of `offersSelfPickup`/`offersSellerDelivery` to stay true — a seller can't disable every fulfillment option.
49. **`FEATURE_MALL_MODE` flag was intentionally NOT implemented this phase.** The global brief lists it as a hard constraint but Phase 1 explicitly left it "fully open for whichever phase owns it," and this phase's own scope section (schema / checkout / seller side / keep the orchestrator working) doesn't mention it. Mall Mode's existing code path was kept fully working and untouched (verified via a live `/m/[mallSlug]` render and reasoning through both changed shared routes — `status` and `verify-otp` — which mall orders fall through unaffected, since `fulfillmentType` defaults to `self_pickup` for them). The flag itself remains for a later phase to add.
50. **TDS u/s 194-O tracking, real Razorpay Route payouts, and the admin T+2 manual-payout batch tool were not touched this phase** — "merchant of record" plumbing beyond the GST bill-breakup line this phase's brief explicitly asked for stays fully open, per the global brief's phase-plan framing (item 2 of the three strategic changes is broader than this phase's fulfillment-model scope).

## Pilot Hardening v2 — Phase 3 (Money: invoices, payouts, tax)

51. **`payoutId` lives directly on `orders`** (nullable FK to a new `payouts` table), not a separate join table. A batch groups many orders into one payout row per seller; tagging each swept order with the payout it landed in is enough to (a) know what's already been paid out and (b) make batch generation idempotent — re-running "Generate T+2 batch" only ever sees orders where `payoutId IS NULL`. Matches the codebase's existing preference for a direct FK over a join table (e.g. `reviews.orderId`, `deliveries.orderId`) when the relationship is one-to-many, not many-to-many. New tables: `payouts` (sellerId, periodStart/End, orderCount, grossSalesInPaise, commissionInPaise, gatewayFeeEstimateInPaise, tds194OInPaise, netPayableInPaise, status pending|paid, paidAt, utrReference, payoutDestinationSnapshot) and `seller_fy_payout_totals` (sellerId + fyLabel unique, grossPayoutInPaise) for the Sec 194-O threshold. Migration `drizzle/0003_panoramic_big_bertha.sql`, via `npm run db:generate` as always.
52. **A payout's `commissionInPaise` is the sum of each included order's own already-stored `commissionInPaise`**, not a fresh recomputation against today's `commissionHomePct`. The brief's "commission (12% default, admin-editable)" is satisfied by the rate already being admin-editable at order time (`/admin/settings`) — summing the historical per-order values means a later rate change can never retroactively rewrite what an already-placed order actually owed. Same reasoning as #38's "don't duplicate an existing admin-editable concept."
53. **`gatewayFeeEstimatePct` (2%) and the Sec 194-O constants (`tds194OPct` 0.1%, `tds194OThresholdPaise` ₹5,00,000) live as fixed `DEFAULTS` in `src/lib/config.ts`, not `platform_config`.** The brief describes the commission rate as "admin-editable" but doesn't say that for the gateway-fee estimate or the TDS rate/threshold — the former is an internal accounting estimate (real Razorpay fees vary by payment method and aren't something an admin should casually retune expecting it to change actual bank costs), the latter is a statutory rate/threshold, same treatment as `gstPct` (#41).
54. **TDS 194-O crossing is an all-or-nothing-per-batch approximation, not a precise pro-rated split of the exact rupee that crosses ₹5,00,000.** `generatePayoutBatch()` adds this batch's gross sales to the seller's running FY total (`seller_fy_payout_totals`, keyed by an Indian Apr–Mar `fyLabel()` e.g. "2026-27"); if the *new* cumulative total exceeds the threshold, TDS applies to the *entire current batch's* gross sales, not just the portion above the line. Documented simplification, verified against a synthetic ₹6,00,000 single-order batch (correctly produced ₹600 TDS = 0.1% of the full amount) — reasonable at pilot scale (a handful of home cooks, each batch easy to eyeball before an actual bank transfer) but should be tightened to a precise threshold-crossing split before scaling to sellers who routinely straddle the line mid-batch.
55. **No "batch ID" grouping concept — a payout row's own `status` (`pending`/`paid`) is what the CSV export and the "needs a transfer" view key off.** "Generate T+2 batch" just inserts however many per-seller `payouts` rows are newly eligible; the CSV export (`/api/admin/payouts/export`) always exports every currently-`pending` row, which is exactly "everything that still needs a manual bank/UPI transfer" — clicking "Generate" again later just adds more pending rows as more orders cross 48h, no separate run/batch identifier needed.
56. **`payoutDestinationSnapshot` freezes `seller_profiles.payoutVpaOrBank` at batch-generation time** onto the payout row itself, rather than the CSV/admin view live-joining `seller_profiles` every time. If a seller updates their UPI ID after a batch is generated but before it's paid, the historical record of what was actually paid-to stays accurate and auditable.
57. **Verified the money math end-to-end against the live dev DB** (`.data/pglite`, discarded afterward) rather than trusting it from reading the code: ran `generatePayoutBatch()` against the real seed data (12% commission, 2% gateway fee correctly derived), confirmed a second run sweeps zero orders (idempotency via `payoutId`), and inserted a synthetic ₹6,00,000 single order for a seller with no prior FY total to confirm the TDS crossing logic fires correctly (₹600 = 0.1%) — see #54. No permanent test file was added for this (unlike `browse.test.ts`'s SQL-boundary test) since it's pure application logic over already-fetched rows, not a SQL translation to verify; `npm test` and `npm run build` both still pass unchanged.
58. **Invoices are issued in the platform's name, not the cook's** — `BRAND.gstin`/`BRAND.registeredAddress` (new fields in `src/lib/config.ts`) are explicit placeholder strings (`'GSTIN-PENDING-REGISTRATION'` etc.) with an inline comment to replace them before a real pilot launch; the invoice page also surfaces a footnote whenever the GSTIN string contains "PENDING". This is deliberate: PadosiPlate is the deemed supplier under Sec 9(5) CGST for home-food orders, so the tax invoice must carry the platform's registration, not the kitchen's — the kitchen is shown separately as "Fulfilled by" for the buyer's reference only.
59. **CGST/SGST is modeled as an even 2.5%/2.5% split of the stored 5% `gstInPaise`, assuming an intra-state supply** — reasonable for a single Hyderabad society pilot where buyer and platform are in the same state, but explicitly worded as guidance ("assuming an intra-state supply... verify... with your CA") rather than a filed determination, since an inter-state edge case would actually need IGST instead. Orders with `gstInPaise === 0` (today, only `mall_pickup` — Mall Mode is deferred anyway) render as a plain "Bill" with no tax lines instead of a "Tax Invoice", so the document never asserts a GST treatment that wasn't actually applied to that order.
60. **Invoice access reuses `GET /api/orders/[id]`'s exact authorization logic** (buyer, the order's seller, the restaurant's manager, or admin) rather than inventing a new rule, and the "View invoice" link on the buyer's order page is gated on `order.status !== 'placed'` (i.e. payment has at least been initiated/captured) — mirrors how the existing OTP-reveal logic on that same page already gates on order state rather than introducing a new payment-status field to thread through the client.
61. **`settlements.ts` (Razorpay Route) gained a "when to enable" README block** per this phase's explicit instruction, listing three preconditions (Route/linked-accounts approved for this business, volume that makes manual transfers a real burden, and TDS/GST reconciled against per-transfer settlement rather than this phase's batch-ledger model) — the interface itself is untouched; the manual T+2 admin batch tool (`src/lib/payouts.ts`, `/admin/payouts`) is the pilot's real payout mechanism.

## Pilot Hardening v2 — Phase 4 (Compliance center refinements)

Every surface pairs it with the same "some categories require a State License — confirm your Kind of Business on FoSCoS" note and explicitly declines to assert either tier as definitive, matching the brief's own wording almost verbatim rather than paraphrasing it into something stronger.

It moves the application to `filed_on_foscos` with the entered ref (mirroring admin's own `'file'` action), notifies admins so they know to track a self-filed application through to grant, and lets `/seller/compliance`'s existing pending-application UI (timeline, grace-window countdown) keep working unmodified for both filing paths. ## Pilot Hardening v2 — Phase 5 (Trust & hygiene)

73. **Schema additions** (migration `drizzle/0005_flowery_silver_samurai.sql`, via `npm run db:generate` as always): `seller_profiles` gained `kitchenPhotosJson` (jsonb string array), `kitchenVideoUrl`, `cookingSinceYear`, `cuisinesJson` (jsonb string array) — kitchen-level onboarding/trust fields, distinct from a per-dish `listings.cuisine`. `reviews` gained `sellerReplyText`/`sellerRepliedAt` (one reply per review — `sellerRepliedAt` doubles as the "already replied" gate, same pattern as other nullable-timestamp gates in this file). `orders` gained `refundInPaise` (cumulative, complaint-driven refunds only — the pre-existing reject-order flow is untouched, still just flips `payments.status` to `'refunded'` with no amount) and `refundDeductedAt` (marks once a refund has been subtracted from a seller payout). `payments` gained `refundedInPaise` (mirrors `orders.refundInPaise`; `status` only flips to `'refunded'` once this reaches the order's `totalInPaise` — a partial refund stays `'captured'` with this field as the running record). `payouts` gained `refundDeductionInPaise`. New table `complaints` (orderId, buyerId, sellerId snapshot, category, description, photoUrl, status, outcome, refundInPaise, resolutionNote, resolvedByAdminId, resolvedAt) plus three enums (`complaint_category`, `complaint_status`, `complaint_outcome`).
74. **No new "is this seller paused" flag** — a complaint's `seller_paused` outcome and the hygiene auto-pause both just flip the pre-existing `sellerProfiles.isApproved` to `false`, the exact same field `/admin/sellers`' manual "Suspend" button already uses (`POST /api/orders` already refuses new orders once `!profile.isApproved`). Introducing a parallel `isPaused` boolean would create two competing "is this seller live" concepts with no clear precedence rule between them; reusing the existing gate means every enforcement point (order creation, browse eligibility) needed zero additional changes.
75. **The hygiene auto-pause counter is computed on demand, not stored** — `PATCH /api/admin/complaints/[id]` counts `complaints` rows with `category='hygiene'`, `status='resolved'`, and an "upheld" outcome (anything except `'rejected'` — `src/lib/complaints.ts`'s `isUpheldOutcome()`) for the seller, every time a hygiene complaint resolves, and flips `isApproved` to `false` once that count reaches `DEFAULTS.hygieneAutoPauseThreshold` (3). Same "compute it lazily, no cron/counter column to keep in sync" philosophy as the FSSAI pending-grace window (#14) and the meal-slot order cap (#43) — at pilot scale (a handful of sellers, a handful of complaints) a full table scan per resolution is free, and a derived count can never drift from the rows it's derived from. Verified directly against the dev DB: 2 upheld + 1 rejected hygiene complaint does **not** trip it; a 3rd upheld one does.
76. **Refunds are a clean top-line deduction on the seller's payout, never a retroactive rewrite of `grossSalesInPaise`/`commissionInPaise`** — same "never rewrite an already-charged historical figure" reasoning as #52 (commission) and #54 (TDS). `orders.refundInPaise` is recorded immediately when an admin resolves a complaint (so the buyer/seller see it right away and `payments.refundedInPaise`/`status` update immediately too), but the actual money is only subtracted from whichever payout batch runs next, via a new `payouts.refundDeductionInPaise` line. Two cases are both handled in `generatePayoutBatch()` (`src/lib/payouts.ts`): (a) the common case — the order hadn't been paid out yet, so its refund is deducted from the very same batch that sweeps it in; (b) the order was **already** swept into an earlier (possibly already-`paid`) payout when the refund happened — its refund is deducted from whichever payout batch runs next regardless, by tracking sellers with any `refundDeductedAt IS NULL` row separately from the normal "new eligible orders" grouping, and creating a payout for that seller even if they have zero newly-eligible orders. Deliberately did **not** try to claw back money from an already-`paid` payout retroactively — that would need a real reversal/reconciliation flow this pilot doesn't have. **Deliberately left `orders.updatedAt` untouched when recording a refund** — bumping it would have re-extended that order's 48h payout hold (`PAYOUT_HOLD_HOURS` in `src/lib/payouts.ts` keys off `updatedAt`), which would silently contradict the brief's "deducted in the **next** payout batch." Verified end-to-end against the dev DB: a ₹50 partial refund on a ₹330 order correctly reduced that seller's payout's `netPayableInPaise` by exactly ₹50, `refundDeductedAt` was set, and a second batch run swept zero further orders/deductions for it (idempotent).
77. **Complaint outcome is a single enum per complaint** (`full_refund | partial_refund | warning | seller_paused | rejected`), not independent flags (e.g. a separate "refund issued" + "warning issued" + "seller paused" triplet) — the brief lists these as the admin's choice of *outcome*, and a single admin action button per resolution (mirroring the FSSAI queue's `file`/`grant`/`reject` action pattern, #16-era admin-queue convention) is simpler to reason about and audit than a multi-checkbox form. If a real complaint ever needs two of these at once (e.g. partial refund **and** a warning), the admin's free-text `resolutionNote` carries that context — building a combinable-outcomes model was judged premature for a single-society pilot.
78. **The 24h complaint window is measured from `orders.updatedAt`**, the same "when did this order's terminal status land" timestamp `src/lib/payouts.ts`'s T+2 hold already uses (#39-era convention) — `verify-otp`'s route already bumps `updatedAt` at the exact moment an order becomes `delivered`/`picked_up`, so no new "delivered at" column was needed. Enforced both server-side (`POST /api/orders/[id]/complaint` hard-rejects past the window) and via a `GET` on the same route that tells the buyer's order page whether reporting is currently possible — mirroring this app's established pattern of never trusting a client-side-only gate for something worth enforcing (10 km radius, slot caps, etc.).
79. **One complaint per order, free-text category+description, no per-item selection** — mirrors the existing review route's "already rated" 409 pattern (`orderId` uniqueness) rather than allowing several open complaints per order. A buyer with more than one issue describes all of them in the single required description field. Kept deliberately lean per the phase brief's "keep this lean" instruction — a structured multi-item complaint model (e.g. flagging specific order lines) was judged out of scope for a single-society pilot.
80. **Kitchen-photo onboarding is a soft nudge, not a hard gate.** The brief's "3 kitchen photos (required)" is enforced as: (a) a new `/seller/onboarding` page (photos required to enable its own "Save & continue" button) that a freshly-registered seller is redirected to instead of `/seller`, and (b) a persistent banner in `src/app/seller/layout.tsx` (same visual pattern as the admin FSSAI-license banner, #69) linking back to that page whenever `kitchenPhotosJson.length < DEFAULTS.minKitchenPhotosRequired` — but **not** a hard redirect/block on every other seller page. Rationale: a hard gate would have broken every pre-existing seeded seller (none of whom had this field before this phase) unless every single one were re-seeded with photos, and would risk locking a seller out of *managing an order already in flight* just because they haven't uploaded photos yet — a materially worse outcome than a visible, repeated nudge. `DEFAULTS.minKitchenPhotosRequired` (3) is a fixed constant, not admin-editable, same treatment as `gstPct`/`tds194OPct` (#41/#53) — a trust/safety threshold, not a pricing lever.
81. **Photo upload happens on a dedicated post-registration page, not inline in the registration form.** `POST /api/uploads` requires a session, which doesn't exist until `/api/auth/register` succeeds — but that route already calls `createSessionCookie()` before returning, so the client is authenticated the moment registration succeeds. Rather than build a second unauthenticated upload path (or hold files in browser memory across the account-creation call), the seller registration flow now does: create account (kitchen name/bio/veg-only only, same as before — keeps "under 10 minutes" honest by keeping this first screen short) → `router.push('/seller/onboarding')` → photos (required) + video/cooking-since-year/cuisines (all optional, per the brief's "everything beyond photos + FSSAI is optional") on that second screen. FSSAI itself was already a separate post-signup step before this phase (`/seller/compliance`) and is left untouched — the onboarding page just surfaces the seller's current FSSAI badge state read-only with a link to continue that existing flow, rather than duplicating the wizard.
82. **`/api/uploads` was extended in place to accept `video/mp4`/`video/webm`** (15 MB cap, vs. images' existing 4 MB) rather than adding a second upload route — same local-disk storage, same auth/validation shape, just a different allowed-type/size branch. 15 MB comfortably covers a ~20s phone-camera clip at typical compressed bitrates without needing any transcoding step (none exists in this codebase).
83. **"Ordered by N neighbours" counts distinct buyers, not orders**, via a new `neighbourOrderCount()` in `src/lib/reputation.ts` (`countDistinct(orders.buyerId)` over that seller's `delivered`/`picked_up` orders) — a single regular customer ordering daily shouldn't inflate the kitchen's apparent reach. Computed per-seller with the same lazy, cached-within-one-request-scope pattern `browseListings()` already uses for `slotSoldOut` (#43) — one query per distinct seller on the results page, not per listing. Shown on both the listing card (`DishCard`, alongside a new "📷 Verified kitchen" signal when `kitchenPhotosJson.length >= minKitchenPhotosRequired`) and the dish-detail kitchen card, matching the brief's four listing-card badges (FSSAI status, kitchen-photos-verified, rating+count, ordered-by-neighbours) end to end.
84. **Seller review replies live on a new `/seller/reviews` page** (+ `GET /api/seller/reviews`, `POST /api/seller/reviews/[id]/reply`), not folded into `/seller/orders` or `/seller/earnings` — matches this app's established one-page-per-concern layout (#48). A reply is permitted exactly once (`sellerReplyText`/`sellerRepliedAt` both null → set together, checked server-side with a 409 on a second attempt) and is shown back to the buyer both on the order-detail page's existing review block and on the dish-detail page's public review list — a buyer should see a kitchen's reply in both the place they left the review and the place other shoppers read it.

Added a `sellerReplyText` to one existing seeded review (demoing the reply feature immediately) and one seeded `complaints` row (`wrong_item`, still `open`) on the Subbalakshmi Tiffins delivered order so `/admin/complaints` isn't empty on a fresh seed — inserted directly rather than through the buyer-facing API, since every seeded "delivered" order is already well past the 24h reporting window (that window is only enforced at the API layer, not a DB constraint, so this is a legitimate seed-time shortcut, not a bypass of real behaviour).

This phase's scope was strictly the trust & hygiene brief (onboarding, listing badges, reviews, complaints); `npm run build` and `npm test` both pass unchanged. The lifetime cap (`referralCreditCapPerUser`) is enforced by counting the referrer's existing `referralCredits` rows at grant time, not a running counter column — consistent with this codebase's general "compute it lazily from real rows" convention at pilot scale. Verified end-to-end against the live dev DB: a referred account's first completed self-pickup order correctly granted the referrer a second ₹30 credit row (`grantedCount` 1→2), and the checkout `useCredit` flow correctly spent an existing credit (`availablePaise` 3000→0, row status `available`→`applied`) with the resulting `totalInPaise` matching the server-computed post-credit amount exactly.

Applied identically to both `home_delivery` and `mall_pickup` order creation (the brief's "apply-at-checkout" wasn't scoped to one order type). The buyer's order-detail page, tax invoice, and checkout bill breakup all render a "Referral credit applied" deduction line whenever it's nonzero — same visual treatment as the existing "Refunded" deduction row (#76).

Seed data pre-features Ammama's Biryani Ghar so the section has a real out-of-the-box case.

Surfaced on the dish-detail kitchen card, the new kitchen profile page (#94), and `/admin/sellers`. At pilot scale (one society, a few hundred orders across 8 weeks) this is simpler and just as fast as pushing every aggregate into SQL. 101. **Week-4 buyer retention is a genuine rolling cohort metric, not a flat "% of buyers active twice."** For the week-N row, the cohort = buyers whose first-ever (non-cancelled) order fell in week (N-3); the metric = what % of that specific cohort ordered again in week N (their 4th week of lifecycle: N-3, N-2, N-1, N). `null` until week 4 (no cohort exists 3 weeks back yet) rather than 0 — a real "not yet measurable" state is different from "measured at zero," and the UI renders `null` as `—`. The kill/pivot checkpoints (#105) use the **latest available** non-null cohort value, not the current week's own (usually-null) one.
102. **"Repeat order rate" is buyer-based, not order-based**: % of THIS week's distinct active buyers who had already ordered in an earlier week (not their first-ever order) — a heavy single repeat customer shouldn't be conflated with genuine week-over-week retention breadth. "Counted orders" (used for this, AOV, fulfillment mix, and net revenue) exclude `status = 'cancelled'` throughout — a cancelled order was never charged and shouldn't distort AOV/revenue, nor count as a buyer "being active" that week.
103. **Seller churn ("no listing in 14 days") is approximated from `listings.createdAt` alone**, since this schema has no listing-level update/deactivation history to reconstruct a true point-in-time "was this seller actively listing on day X" timeline (`listings` has `createdAt` only, no `updatedAt`). A seller counts as churned for week N if, among APPROVED sellers who'd registered (by `users.createdAt`) before that week's end, none of their listings has a `createdAt` inside the trailing 14 days of that week's end — i.e., "posted/refreshed something recently," not "currently has an active listing" (the latter would make an established seller who simply never touches their menu again look perpetually non-churned, which defeats the point). Documented simplification, same spirit as #54's TDS-batch approximation — reasonable at pilot scale, would need a real listing-activity log to do precisely at larger scale.
104. **Net revenue per order = (commission + buyer platform fee − estimated gateway fee − refunds) ÷ order count**, deliberately **excluding GST** (the platform collects it only to remit to the government as the Sec 9(5) CGST deemed supplier — never its own revenue, see #41/#58) and applying the gateway-fee estimate (`DEFAULTS.gatewayFeeEstimatePct`) against `totalInPaise` (the actual amount that moved through the gateway) — **not** `subtotalInPaise` the way `src/lib/payouts.ts`'s seller-payout ledger uses it. Those are two different estimates for two different purposes: payouts.ts is estimating a cost attributable to what the *seller* is owed; this is estimating the *platform's own* processing cost on the full amount it actually processed. Refunds are attributed to the week the underlying order was **placed** (not the week the refund was resolved), keeping "net revenue per order this week" a coherent per-cohort-of-orders figure rather than a mix of two time periods.

Week-8 thresholds start below the steady-state figures (20% penetration / 8% retention) since an 8-week-old pilot isn't expected to already be at the mature 35%/15% bar used for week 14.
106. **"Pilot week" (which gates whether a checkpoint is `due`) is derived from the society's real earliest buyer registration**, not from "how many rows does the weeks table have" — `Math.floor((now − earliestBuyerCreatedAt) / 7days) + 1`. Caught by inspecting the actual seeded fulfillment-mix numbers (one week showed 0% seller-delivery despite the pattern intending ~50%), not assumed correct from the code alone.

Same "compute it lazily from real rows, don't cache a flag that can drift" convention this codebase already uses for the hygiene auto-pause counter (#75) and badge tiers (#93) — a stored "prior status" field could silently go stale the moment a seller's application state changes while their license entry is still pending review, whereas a derived value never can.

(b) The dialog's outer container changed from a single `overflow-y-auto` box to a `flex flex-col overflow-hidden` box with two children: an inner `min-h-0 flex-1 overflow-y-auto overscroll-contain` scrollable body (title + `children`), and an optional `footer` prop rendered as a non-scrolling flex sibling below it. `overscroll-contain` stops an over-scroll at the top/bottom of the body from "leaking" into a rubber-band scroll of the page behind it (mainly an iOS Safari behaviour — the body-overflow lock in (a) is the primary, cross-browser fix; this is defense-in-depth). ## Phase 1 Pilot

Every ambiguous call made while turning the codebase into the PadosiPlate pilot. Earlier entries about payouts, merchant-of-record and platform delivery are superseded by this section.

### Money model
- **Platform never touches food money.** Buyers pay food directly to the kitchen (UPI VPA or at pickup); Razorpay carries only subscription payments and the buyer platform fee. The old merchant-of-record/payout flow is disabled. The `payouts` tables are retained (history/migrations) but unused; no bank account numbers or PAN are collected.
- **Platform delivery disabled** for the pilot (`platform_delivery` is no longer offered at checkout); kitchen delivery and self-pickup remain.
- **Two-part order money columns** on `orders`: `food_total`, `platform_fee`, fee GST, `fee_bps_snapshot`, `food_payment_mode`/`status`, etc. `online_charge` is kept as the amount actually paid online (= the platform fee after credit), so existing readers keep working.
- **Integer paise / basis points** everywhere; fee = floor(food × bps) then floor/cap; GST is added only when a platform GSTIN is set; ECO-GST-on-food is a separate switch (off) pending CA advice.
- **Referral credit applies to the fee only, before GST.** It is reserved when the order is placed, consumed on payment and released on expiry/cancel/refund (rows are split so partial use is exact).
- **Razorpay ₹1 minimum:** a fee that falls below ₹1 after credit is rounded up to the ₹1 minimum top-up (or treated as paid if fully covered by credit).
- **Rates are snapshotted** on each order and each subscription payment; changing a setting never rewrites history (e2e scenario 7).
- **Subscriptions:** periods stack when renewing early; status is *derived* from dates (`active → grace → expired`) so a missed cron cannot leave a kitchen visible; grace length is a setting. A kitchen without an active/grace/waived subscription is hidden from buyers but nothing is deleted.
- **Refunds reserve first:** the refundable amount is reserved atomically in the DB before Razorpay is called, so a double click or retried webhook cannot over-refund. Food refunds are the kitchen's liability and are tracked as "kitchen refunds due" (the platform does not move that money).

### Payments correctness (audit S1/S2)
- Verify route checks order ownership, amount and signature length; webhooks dedupe through `webhook_events`, never downgrade a captured payment and assert the amount; `markOrderPaid` is exactly-once via a conditional `UPDATE … RETURNING`.
- Unpaid orders expire and release reserved stock and credit.

### Auth, admin, sessions
- **E-mail tokens are random and stored hashed** (not JWT-signed): they can be revoked, single-use and are not forgeable if `JWT_SECRET` leaks.
- **Unverified users may still browse and order**, with a persistent banner to verify; only admin access requires a verified e-mail.
- **Admin = `ADMIN_EMAILS` + verified e-mail only.** The allowlisted account is created with a one-time password and `must_change_password`; nobody else can be promoted through the app. `ADMIN_BOOTSTRAP_PASSWORD` exists only so e2e can log in deterministically.
- **DB-backed sessions** (revocable, "log out everywhere") with a JWT cookie carrying the session id; a sliding refresh is done in `src/proxy.ts`.
- **`src/proxy.ts` now exists** for two cross-cutting jobs only: CSRF `Origin` check on mutating `/api/*` requests and sliding session refresh. Role checks stay in layouts and handlers.
- Postgres fixed-window **rate limiter** shared by all instances (login, register, reset, uploads, messaging). It is bypassed only when `E2E=true` and `NODE_ENV!=='production'`.

### Kitchens, moderation, messaging
- Kitchen state machine `draft → submitted → changes_requested | approved | rejected`, and `approved ↔ delisted`. A dish re-enters review when it is new, its name or photo changes, or its price moves by more than 30%.
- Admin ↔ kitchen messaging is a per-kitchen thread with reusable templates; delisting notifies the kitchen and can be undone (relist).
- Buyer ↔ kitchen threads are per order and anonymous (first names/handles, no phones); either side can block.
- The **restaurant/Mall console** is behind `restaurantConsoleEnabled` and off for the pilot.
- A **tower** column was added to kitchens for tower/block-level fulfilment grouping.
- A **GeocodeAdapter** was created because none existed (mock by default; live when `GEOCODE_API_KEY` is set).

### FSSAI assistant
- Never asks for or stores FoSCoS credentials/OTPs and never claims to file for the seller. Aadhaar masking is done in the browser by blacking out pixels before upload (and the server requires the "masked" attestation). The gate also enforces licence expiry. Funnel events and walkthrough steps are stored in the DB so admin can edit wording without a deploy.

### Infrastructure and ops
- DB is **required in production** (no silent PGlite). `db:bootstrap` runs migrations and idempotent production data only.
- Uploads go through a **StorageAdapter** (local / replit / s3) with magic-byte validation, EXIF stripping + resize, AES-GCM at rest for id/address proofs and a retention purge job.
- Times are stored UTC and rendered/sliced in **IST** (`src/lib/time.ts`).
- **Dev-only endpoints:** `/api/dev/outbox` (non-production) and `/api/dev/time-travel` (requires `E2E=true` and non-production; used by e2e scenario 9). Both 404 in production.
- **Fonts are copied into the repo** (`src/fonts`, `next/font/local`) so the app makes no calls to Google Fonts.
- Legal pages are drafts, clearly labelled, to be reviewed by a lawyer.

### Tests
- Vitest (PGlite) covers fee maths, subscriptions, state machine, auth, payments/webhooks, refunds, moderation, threads, CSRF, FSSAI and a repo-wide scan that fails on legacy brand names. Playwright runs the ten required journeys plus 390px mobile checks (no horizontal scroll, ≥36px targets, AA-checked palette).
- Bug found by e2e and fixed: the cart was wiped on every full page load because the persist effect ran before hydration.
